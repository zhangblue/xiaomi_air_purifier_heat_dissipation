# v0.1.0 GitHub Release 执行计划

> **面向 AI 代理的工作者：** 必需子技能：使用 superpowers:subagent-driven-development（推荐）或 superpowers:executing-plans 逐任务实现此计划。步骤使用复选框（`- [ ]`）语法来跟踪进度。

**目标：** 从已验证的 `main` 构建 macOS arm64 与 Linux x86_64 运行包，为 `v0.1.0` 创建 GitHub Release 并上传包与 SHA-256 校验文件。

**架构：** 两个平台分别从当前源码全新构建，目录包分别归档并审计。Release 使用首发中文说明与四个附件；tag 必须指向包所对应的同一个提交。缺少 GitHub 发布权限时停止在已验证的本地产物，不将未发布内容表述为已发布。

**技术栈：** Python 3.11、PyInstaller、OrbStack/Docker Linux amd64 容器、`tar`、`shasum`、Git/GitHub Release。

## 文件职责

- `docs/superpowers/specs/2026-10-25-v0.1.0-release-design.md`：已批准的发行边界，不再修改。
- `docs/superpowers/plans/2026-10-25-v0.1.0-release.md`：本执行清单。
- `dist/`：Git 忽略的构建目录，仅保存新产物；不读写用户的旧产物。
- 临时 Release 正文：向 GitHub 发布的中文说明，不纳入源码包。

### 任务 1：构建并审计两个运行包

- [ ] **步骤 1：锁定输入。** 在项目根目录运行 `git status --short --branch`、`git rev-parse HEAD`、`git tag --list v0.1.0`、`git ls-remote --tags origin refs/tags/v0.1.0`；确认工作树除未跟踪的本机 `config.toml` 外无改动、tag 尚不存在。运行 `.venv/bin/python -m unittest discover -s tests -v`，预期 109 项通过。
- [ ] **步骤 2：全新构建 macOS 包。** 先确认 `dist/purifier-control-v0.1.0-macos-arm64` 不存在，然后运行 `.venv/bin/python -m tools.build_bundle --output dist/purifier-control-v0.1.0-macos-arm64`。检查 `app/purifier-control --help` 的退出码、`file app/purifier-control` 的 arm64 架构、`check.command` 和 `run.command` 的可执行位。不得执行 `check.command` 或 `run.command`。
- [ ] **步骤 3：全新构建 Linux 包。** 启动当前已安装的 OrbStack Docker 引擎。遵循 `docs/bundle-build.md` 的 Mac 容器流程，用 `mktemp -d` 创建临时目录，仅把 `pyproject.toml config.example.toml src tools README.md tests docs` 复制进去；不得复制或挂载仓库根目录。Linux amd64 容器安装 `gcc libc6-dev` 后运行测试及 `python -m tools.build_bundle`，在只读挂载的容器中执行 `app/purifier-control --help`；复制整个产物到尚不存在的 `dist/purifier-control-v0.1.0-linux-x86_64`。检查二进制 `ELF x86-64` 与两个 `.sh` 脚本可执行。
- [ ] **步骤 4：归档与安全审计。** 以各平台目录为顶层分别生成 `purifier-control-v0.1.0-macos-arm64.tar.gz`、`purifier-control-v0.1.0-linux-x86_64.tar.gz`；各生成 `<包名>.sha256`。列出归档路径并确认不含 `config.toml`、`.secrets`、`purifier-token`、`.git`、`.venv`、`__pycache__` 或 `.pyc`；校验 `shasum -a 256 -c` 两份校验文件。保留构建与审计的命令、退出码和结果。

### 任务 2：发布 tag、Release 与附件

- [ ] **步骤 1：准备中文 Release 正文。** 标题按规格使用“净化器温控 v0.1.0 — 首个跨平台源码与双平台运行包”。正文包含更新亮点、主要功能、稳定性与安全、四个附件的下载表、目标机配置与 `check`→`run` 顺序、Windows 未附包及 Linux 真机验收边界；对外链接采用实际 `v0.1.0` 下载 URL。不得写入 IP、token 或本机配置内容。
- [ ] **步骤 2：核对发布目标。** 再次确认本地 `main` HEAD 与任务 1 输入 SHA 完全一致，`v0.1.0` 本地和 GitHub 均不存在，`origin/main` 不含未预期的新提交。若 GitHub 身份验证不可用，先请求用户完成登录，不得创建不一致的 tag 或部分 Release。
- [ ] **步骤 3：推送并创建。** 先把本地 `main` 推送到 `origin/main`；以已核对的 HEAD 创建附注 tag `v0.1.0` 并推送。创建非草稿、非预发布的 GitHub Release，上传四个已审计文件，发布正文使用步骤 1 的内容。不得覆盖已有 tag/Release，也不得强推。
- [ ] **步骤 4：远端核验。** 从 GitHub 读回 Release，逐项核对 tag、目标 SHA、正文标题、四个附件名称/大小，并提供 Release 页面链接。若上传失败，准确报告哪些步骤已完成以及可继续的状态；不声称发布完成。
