# 电脑温度联动米家空气净化器 Pro：设计说明

日期：2026-09-30
状态：方案已确认，待用户审阅书面规格

## 目标与范围

开发一个在 macOS 或 Windows 电脑上运行的常驻命令行程序。第一版由用户手动启动；启动后将米家空气净化器 Pro（机身型号 AC-M3-CA）打开、切换到最爱档，并使用配置的低温风速级别。当电脑 CPU 温度持续高于 60°C 时，将最爱档级别调到配置的高温值；温度回落后调回配置的低温值。两个温度区间始终使用最爱档，默认高温级别为设备验证过的最大值，低温级别为用户配置的较低值。

同一套控制逻辑支持两个系统，温度采集方式由配置选择。第一版无需图形界面、开机自启、云端服务或 Home Assistant。净化器只负责增加空气流动；程序不控制电脑自身风扇，也不承担过热保护职责。

## 设备与环境前提

- 净化器机身型号已确认为 AC-M3-CA，已接入局域网且可在米家 App 中控制；当前内网 IP 为 `192.168.250.118`。运行电脑需能访问该地址；若路由器以后改变净化器 IP，需更新配置，建议在路由器中为设备保留该地址。
- 已从绑定设备的米家账号取得局域网访问 token，并保存在项目的 `.secrets/purifier-token` 文件中；文件权限为仅当前用户可读写，`.secrets/` 已加入 `.gitignore`。程序可从此文件或用户环境变量读取 token，不将其写进普通配置或日志。
- 米家账号返回的设备内部型号已确认为 `zhimi.airpurifier.v6`，内网 IP 为 `192.168.250.118`。程序首次局域网连接仍须查询并核对设备报告的型号；不符时停止风速控制并报告诊断信息。
- 首次设置需在真机上验证高、低两个最爱档级别，尤其是作为默认高温级别的最大值。`python-miio` 的通用参数范围不能直接当作这台设备固件的实际可用级别。
- 第一版由用户从终端手动启动，程序持续运行至用户主动停止或电脑关机。启动入口保持单一且无需交互输入，以便后续直接交给 macOS LaunchAgent 或 Windows 任务计划程序调用。第一版不创建或安装任何自启配置。

## 推荐架构

使用 Python 实现常驻主程序，划分为四个职责清晰的部分：

1. **温度采集器**：统一返回带时间戳的 CPU 温度（°C），或明确的读取错误。macOS 调用 `smctemp -c`，兼容 Intel 与 Apple 芯片；Windows 使用一个基于 LibreHardwareMonitor 的小型本地采集辅助程序，优先选 CPU Package 温度，若无该传感器则使用已配置的 CPU Core 汇总值。辅助程序只向主程序输出温度，不直接控制净化器。对缺失传感器、无效数值和权限不足给出可识别错误。
2. **规则引擎**：只接收温度与时间，不依赖操作系统或净化器库。维护高温级别、低温级别、传感器故障三类运行状态和连续计时；两个目标级别由配置提供。
3. **净化器适配器**：通过 `python-miio` 在局域网读取状态、开机、设置最爱档级别及切换到最爱档模式。对规则引擎暴露统一的“应用最爱档级别”操作；每次操作后读取状态确认，失败时有限重试，避免密集发送命令。
4. **运行与配置**：读取配置、启动采集和控制循环、记录事件与错误；提供一次性的设备/传感器检查入口。后台运行逻辑不依赖终端交互，也不假定固定工作目录，为后续接入系统自启机制保留入口。

这种结构让 macOS、Windows 共用规则引擎与净化器控制；以后更换传感器工具只需替换温度采集器。

## 配置

示意配置如下；真实 token 从单独的私有文件读取，文件路径相对配置文件所在目录解析：

```toml
[system]
platform = "macos"          # macos | windows；按运行电脑的系统填写
temperature_sensor = "cpu"  # 第一版固定使用 CPU 温度
sample_interval_seconds = 5

[purifier]
host = "192.168.250.118"
expected_model = "zhimi.airpurifier.v6"
token_file = ".secrets/purifier-token"

[control]
high_temperature_c = 60
high_duration_seconds = 15
recover_temperature_c = 55
recover_duration_seconds = 120

high_favorite_level = 17     # 示例最大级别；首次设置时必须在真机上验证
low_favorite_level = 3       # 示例低速级别；首次设置时必须在真机上验证
```

`platform` 必须明确设置为 `macos` 或 `windows`，程序据此选择温度采集器；配置值与当前系统不匹配时直接报错。Windows 采集器的具体 CPU 传感器标识可另行配置，以避免多 CPU 或主板传感器被误选。

`high_favorite_level` 和 `low_favorite_level` 分别配置高温、低温时的最爱档级别，均为整数；它们不是精确转速或百分比。高温级别必须大于低温级别。配置检查应拒绝恢复阈值不低于升档阈值、无效持续时间、缺少的级别与超出库支持范围的级别。设备是否真正接受两个级别由首次真机检查确认。

## 运行规则

| 条件 | 动作 |
| --- | --- |
| 程序启动且净化器可连接 | 开机，写入低温级别，切换到最爱档，并开始采样。 |
| CPU 温度严格高于 60°C，连续至少 15 秒 | 写入配置的高温最爱档级别，保持最爱档模式。 |
| 高温状态下，CPU 温度严格低于 55°C，连续至少 120 秒 | 写入配置的低温最爱档级别，保持最爱档模式。 |
| 温度在 55°C 至 60°C（含边界）之间 | 保持当前最爱档级别，避免来回切换。 |

持续时间按采样时间戳计算，而不是只数样本数量。任一采样值不满足当前进入条件，就重置该条件的连续计时；无效样本既不触发高温级别，也不触发低温级别。状态未变化时不重复写入净化器。程序重启后以实际净化器状态为基础重新校准，并按启动规则设为最爱档及低温级别；若此时温度持续超阈值，15 秒后再应用高温级别。净化器只有一个当前最爱档级别，因此每次跨越温度区间时都要写入对应级别。

## 异常与手动操作

- **局域网暂不可用**：保持进程运行，采用有上限的退避重试；连接恢复后查询真实状态，再执行当前规则对应的动作。
- **温度读取失败**：记录故障并继续重试；不把故障读数视为低温，不主动切换级别。启动时无法读取温度，仍尝试开机并应用配置的低温最爱档级别，同时报告传感器故障。
- **净化器拒绝配置的级别**：不猜测下一档，也不反复发送；保持当前可用级别，提示重新验证级别配置。
- **用户在米家 App 或面板手动改档**：第一版在下一次需要切换状态时按规则重新控制。状态稳定时不持续覆盖手动选择；若需要“手动暂停自动控制”，留作后续功能。
- **程序停止、电脑睡眠或关机**：不主动关闭净化器；恢复运行后重新读取温度和设备状态。

## 验收标准

1. macOS（Intel 或 Apple 芯片）与 Windows 均能通过对应采集器读到有效 CPU 温度；传感器不可用时给出明确错误。
2. 两个平台使用相同配置字段和规则引擎，通过切换 `platform`/采集器运行，无需改动判断或净化器控制代码。
3. 用户在 macOS 或 Windows 上手动启动程序后，程序持续运行并打开净化器；网络晚于程序就绪时也能最终连接。关闭终端或停止进程后的行为在使用说明中明确告知。
4. 使用模拟温度序列验证 60°C/55°C 阈值、15 秒/120 秒持续时间、边界值及读取失败；只在状态变化时发送控制命令。验证高、低两个配置级别均在最爱档模式下生效。
5. 真机验证开机、切换到最爱档、配置的高低温级别及两者切换，并确认设备报告的型号与配置一致。
6. token 不出现在仓库、普通配置示例和日志中。
